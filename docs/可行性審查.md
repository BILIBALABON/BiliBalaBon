# 原 prompt 的可行性審查

## 結論

**可行，但不能照原文執行。** 原 prompt 有一個不存在的參數、缺少整套迴圈賴以運作的「通過條件」，
並且把三件模型做不到的事當成做得到。補上這些之後，系統已經實作出來並實際跑過（驗證範圍見文末）。

優化後的 prompt 在 `docs/Prompt.optimized.md`。

## 一、技術敘述的錯誤與不精確

以下都對照 Claude Code 2.1.296 與 claude-agent-sdk 0.2.159 實測或查閱官方文件。

| 原文 | 問題 | 修正 |
|---|---|---|
| 用 `max_budget_ntd` 設花費上限（新台幣） | **這個參數不存在。** SDK 只有 `max_budget_usd` | 設定檔以新台幣設定預算與匯率，orchestrator 換算成 `max_budget_usd` |
| 「上限三道：`--max-turns`、`max_budget_usd`、迴圈次數」 | 方向正確，但 `max_budget_usd` 是事後檢查的軟上限：實測上限 0.0005 美元的 session 花了 0.012 美元才停 | 另加專案層級的累計上限；單一 session 的上限取「階段比例」與「剩餘預算」較小者 |
| `--allowedTools` 只列必要工具 | 在 SDK 裡 `allowed_tools` 只是自動核准清單，**不會限縮工具**。唯讀的審核者若只設它，仍然拿得到 Write | 用 `tools` 限縮工具集，`allowed_tools` 放路徑限定的核准規則 |
| reviewer 唯讀（Read, Grep, Glob） | 唯讀的 agent 無法把審核結果寫成檔案，後續流程拿不到結果 | 審核者用結構化輸出（`--json-schema`／`output_format`）回傳，由 orchestrator 代寫 |
| （未提及） | 實測：`--agent <名稱>` 加上該 agent 有 `tools` 清單時，`structured_output` 是 null | 以 `system_prompt` + `tools` 啟動角色，不用 `--agent` |
| `dontAsk`：「拒絕所有需要確認的動作」 | 正確。但要補充：寫入與 Bash 都必須有允許規則才會動；`Bash(npm *)` 不涵蓋 `npm test && …` 這種複合指令 | 規則限定到路徑與指令：`Write(/work/**)`、`Bash(python3 -m learnloop.gates *)` |
| Stop hook「一定要加退出條件」 | 正確，但沒說 hook 怎麼知道該檢查什麼。同一支 hook 在不同階段要檢查不同的東西 | 由環境變數傳入專案與階段；沒有變數時直接放行；退出條件三個（通過／攔截次數／閘門自己壞掉） |
| 外層迴圈第二輪的 prompt 是「npm test 仍失敗，請修復」 | 沒有把失敗訊息帶回去，agent 得自己重新找原因；也沒檢查 `claude` 是否真的有回傳結果 | 每輪把閘門的錯誤訊息放進 prompt；檢查 `subtype`、累計花費；加 `< /dev/null` |
| `isolation: worktree`、`-w` | 需要 git repo，而且是給「改程式碼」用的。內容管線的 agent 各寫各的輸出檔，用不到。實測另外發現 `-p` 建立的 worktree 會被鎖定，`git worktree remove` 前要先 `unlock` | 隔離改用「每個 agent 只能寫 `work/`、各寫自己的檔案」；worktree 只留給開發系統本身的腳本 |
| `/loop`、Routines、GitHub Actions 自動觸發 | 三者的說明正確（`/loop` 7 天過期、Routines 最短 1 小時）。但 Routines 與 Actions 在雲端執行，**碰不到本機的上傳檔、語音辨識與監控介面** | 本機自動觸發改用收件匣監看（`learnloop watch`）；雲端排程只做 repo 的例行檢查 |
| `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` 限制並行數 | 變數存在（預設 20），但它管的是單一 session 內的 subagent；多個 `query()` 之間的並行它管不到 | orchestrator 用 semaphore 限制同時執行的 session 數，並把這個變數一併傳入 |
| `bypassPermissions` 只在容器裡用 | 正確；另外它不能以 root 執行 | 本系統完全不使用 |

## 二、缺少的定義（影響最大）

1. **沒有「通過」的定義。** 原 prompt 的迴圈範本以 `npm test` 為終止條件，但目的是整理學習資料，沒有測試可跑。
   沒有機械化的通過條件，外層迴圈與 Stop hook 都無從判斷。
   → 為每個階段寫確定性的閘門（格式、必要段落、來源標示、主張與更正的對應、連結是否存在、版面上限、審核分數）。
2. **沒有資料契約。** 多個 agent 接力，卻沒規定誰產出什麼檔案、什麼格式。→ 固定的專案資料夾結構與 JSON Schema。
3. **「簡報」沒有指定格式。** → 單檔 HTML（可離線、可列印成 PDF）為主，另輸出可編輯的 `.pptx`。
4. **「即時回覆系統處置方案」語意不明。** → 定義為處置單：系統遇到無法自行解決的事就暫停，在彈窗列出建議方案，使用者選擇後立即繼續。
5. **沒有中斷續跑、錯誤處理、無人值守時的行為。** → 狀態落檔、已通過的階段不重跑、處置單逾時採保守預設。
6. **排版瑕疵**：`#任務` 少了空格不會成為標題；程式碼區塊被切斷；`5.1` 的層級不清。

## 三、模型做不到、原文卻預設做得到的事

| 原文的期待 | 實際 | 處理 |
|---|---|---|
| 音檔、影片整理 agent | Claude 不能直接聽音檔或看影片 | 前處理：ffmpeg 抽音軌與關鍵畫面 + 語音辨識（faster-whisper 或自備字幕檔） |
| 透過書籍查證與補充 | Claude 讀不到未公開的書籍 | 使用者上傳參考資料（標為 reference）；其餘只能用網路公開來源 |
| 安排說明影片網址 | 模型會編出不存在的網址 | 閘門實際連線檢查每個網址（YouTube 用 oEmbed），失效就退回 |

## 四、實際執行與獨立審查後才發現的問題（已修正）

這些是把系統跑起來、再請另一個沒看過開發過程的 agent 找碴之後才看到的，原 prompt 與第一版設計都沒料到。
它們也說明了為什麼優化後的 prompt 把「實際執行」與「獨立審查」列為驗收條件。

**真實執行時發現：**

1. **審核者與閘門互相打架。** 審核者把「11 張超過目標 8 張」列為重大問題並建議刪掉參考資料頁與影片頁，
   而閘門要求這些頁面必須存在，編排者被夾在中間。→ 在審核者的規則裡明訂版面結構不在審核範圍，並在任務說明寫出允許的張數範圍。
2. **沒有網路時，連結檢查會把所有連結判成失效**，agent 會白白重試。→ 連不到任何常見網站時改判為「系統問題」，
   不再呼叫 agent，直接開處置單（重新檢查／這次不檢查連結／停止）。閘門的結束碼因此分成 1（內容沒過）與 3（檢查無法進行）。
3. **查證與補充比預期貴很多。** 兩份很短的樣本用最便宜的模型，查證＋補充就佔了總花費的三分之一以上。→ 預設預算調高，說明文件寫明實測數字。
4. **示意圖的字小到看不清楚。** 模型沒有照「字級 22 以上」做。→ 閘門檢查每個文字的字級（含繼承與沒寫的情況）。
5. **測驗題解說寫「選項 2」，畫面上顯示的卻是 A、B、C。** → 編排者的規則明訂用字母。

**獨立審查發現（都已修正並補上測試）：**

6. **重跑會被舊檔案騙過。** 指定「從某階段重跑」時，如果 agent 這次失敗、什麼都沒寫，閘門會因為上次留下的檔案而通過。→ 重跑前先刪掉該階段與之後的產出。
7. **執行過後再加檔案不會被處理。** → 記錄來源清單的指紋，有變動就從頭來過；沒變的檔案沿用轉檔與擷取結果。來源代號也改成只增不減。
8. **示意圖可以夾帶跳出 SVG 的 HTML 元素**（`<meta>` 轉址、`<form>` 按鈕），黑名單擋不完。→ 改成白名單：只留畫圖需要的元素與屬性。
9. **審核結果的分數欄位可以夾帶 HTML 在監控介面執行。** → 介面一律跳脫，後端也先驗證格式才送出。
10. **教材可以引用自己當查證依據**，於是所有主張都「已查證」而沒有任何外部來源。→ 只有標為參考資料的上傳檔與網址算證據。
11. **按停止後行程其實還在跑。** 背景執行緒裡的語音辨識不理會停止訊號，狀態卻已顯示「已停止」，還可能被重複啟動。→ 狀態存檔後直接結束行程；後端以行程本身是否存活為準。
12. **Stop hook 把「Python 當掉」誤認成「內容沒過」**（兩者結束碼都是 1），agent 會被一段錯誤訊息擋住。→ 只有帶著「閘門未通過」字樣的失敗才攔截；攔截次數改成每一輪重新計算。
13. **同一台電腦上其他連接埠的網頁可以操作這個介面。** → 寫入類請求必須來自完全相同的 host:port。
14. **連結檢查會照模型給的網址去連內部網路位址**；含中文的網址被誤判為失效。→ 拒絕本機與內部位址（含轉址後的目的地）；網址先編碼再檢查。
15. 其他：清空張數欄位會讓每次執行都失敗；沒有音軌的影片無法處理；UTF-16 文字檔變亂碼；逐字稿的時間標籤會落後一段；
    超過檔名位元組上限的中文檔名讓整批上傳失敗；平行的 worker 會對同一件事問兩次。

## 五、驗證範圍

**實際跑過、確認運作的：**

- 自動測試 56 項（不呼叫模型、不需外部網路）：閘門、外層迴圈、審核退回、處置單、預算、續跑與重跑、來源變動、
  Stop hook、連結檢查、前處理、示意圖清洗、API 安全、停止。其中關鍵的十幾項做過「故意改壞程式，測試是否會失敗」的確認。
- 監控介面：以無頭瀏覽器走完「建立專案 → 上傳 4 個檔案 → 開始 → 處置彈窗 → 重試與審核退回 → 完成 → 開啟成品」（模擬模式），
  並確認帶有 HTML 的標題、檔名、紀錄與審核內容都只會顯示成文字。
- 真實 session（最便宜的模型）：平行擷取、agent 自己跑閘門、Stop hook 攔截、審核者的結構化輸出、多輪審核與退回修改
  （含「筆記有錯先退回整合修訂」的路徑）、預算用完自動暫停並採保守預設、追加預算後從中斷處續跑、出版。
  驗證合計花費約 5.3 美元：第一次完整流程 3.8 美元；修正上述問題後從「編排簡報」重跑一次 1.4 美元；其餘是小型探測。
- headless 腳本 `scripts/loop.sh`：真實執行，包含「第一輪沒過 → 帶錯誤訊息 resume → 第二輪通過」。
- `scripts/dev-loop.sh`：真實執行，確認 `-p -w` 會建立 worktree、變更只落在 worktree 內，以及清理前要先解除鎖定。
- 前處理：影片抽關鍵畫面、沒有音軌的影片、字幕檔轉逐字稿、缺少語音辨識引擎時開處置單；
  語音辨識的串接以「介面相同的替身引擎」測過（時間戳、暫存檔清理、辨識途中停止）。

**沒有驗證的（請自行確認）：**

- **真正的 faster-whisper**：測試環境無法下載模型。串接邏輯測過，辨識品質與速度沒有。
- **對真實網站的連結檢查與 YouTube oEmbed**：測試環境連不到外部網站，只對本機假網站驗證了判定邏輯。
  真實執行時連結檢查是在「只警告」模式下跑的。
- **預設模型（sonnet／opus）的成品品質與花費**：真實執行為了省錢全程用最便宜的模型。
- **`.github/workflows/` 的兩個工作流程**：寫好但沒有執行過。
- **Windows**：停止功能用到行程群組訊號，只在 Linux 測過；macOS 預期可用，Windows 需要調整。
- **長教材**：一小時以上的逐字稿會不會超過單一 session 的 context，沒有測。

## 六、模型選型（2026 年 10 月更新）

原本的 agent 檔只寫了別名（多數 `sonnet`、審核者 `opus`），沒有考慮各 agent 的任務差異，也沒有指定思考深度。
這次依任務特性為每個 agent 重新選型，原則、價格與每個 agent 的理由見 `docs/模型選型.md`。重點：

- 逐檔平行、照格式忠實擷取的 ingest-document 改用 Haiku 5.5；來源要看圖（掃描檔、照片）時改用 Opus 5.5。
- 讀關鍵畫面的 ingest-video、決定全局結構的 planner、最後把關的 reviewer 用 Opus 5.5。
- 其餘維持 Sonnet 5.5（slide-composer 改用 high effort）。每個 agent 都明確指定 effort 與備援模型（審核者不設備援）。
- model 一律寫完整 ID，不用會隨版本漂移的別名。
- 專案搬到獨立的 SmartLearn repo（放在根目錄，保留 commit 歷史）。依擁有者決定，原規格的每週排程相容性檢查（claude-code-action）不納入，GitHub Actions 只保留 CI 測試。

**這次驗證的：**

- 自動測試 69 項全部通過。新增的選型、session 隔離、張數上限等測試，都做過「故意改壞程式，測試是否失敗」的確認；
  GitHub Actions 的 CI 工作流程在 pull request 上實際執行並通過。
- 真實呼叫：三個模型 ID、`--effort` 與 `--fallback-model` 都被 CLI 接受；審核者在 Opus 5.5 上的結構化輸出可用。
- 真實流程（所有 agent 統一用 Haiku 5.5，實際花費 US$0.655）一路跑到第三輪審核。途中發現並修正：
  1. SDK 0.2.159 內建的 CLI 不認得 5.5 世代的模型，花費被高估約 35 倍，預算上限跟著失準 → 要求 0.2.165 以上，doctor 會檢查。
  2. 從 Claude Code（雲端 session、`/loop`）裡啟動時，所有 agent 共用上層的 session ID：平行的 agent 寫進同一份紀錄，
     重試時 resume 可能接到別的 agent 的對話 → 清空繼承來的變數。以真實呼叫確認兩個平行 session 各自獨立、resume 接回正確的對話。
  3. agent 在閘門指令後面加 `; echo "exit=$?"`，被 dontAsk 拒絕，第一層「自我檢查」完全沒作用 → 共同規則寫明要單獨執行；
     修正後實測 agent 自己跑閘門成功。
  4. 期望 6 張卻排了 4 章，加上每章一題測驗，編排者怎麼改都過不了張數上限 → 大綱閘門依允許的張數限制章節數；
     修正後編排第一輪就通過閘門。
  5. 審核者要求刪掉定稿筆記裡的 `[secN]` 與「（未能查證）」，但前者是閘門要求、後者是整合規則要求 → 列入審核者「不在審核範圍內」。
- 獨立審查（沒參與開發的 agent）找到的問題：每週相容性檢查缺 GitHub token、測試受 `config.toml` 的 override 與環境變數影響、
  `scripts/dev-loop.sh` 在子資料夾裡失效、doctor 沒檢查系統 CLI 的版本、frontmatter 註解的解析與 YAML 不一致、
  `scripts/loop.sh` 在 bash 3.2 的空陣列問題、統一覆寫時做的擷取結果會被沿用。都已修正並補上測試；
  `scripts/dev-loop.sh` 以真實執行確認（含 resume）。

**這次沒有驗證的：**

- 本選型的成品品質與實際花費：真實流程為了省錢統一用 Haiku 5.5，花費是依實測 token 用量推估（見 `docs/模型選型.md`）。
- 執行環境的網路政策擋掉外部網頁，WebFetch 全部失敗，所以查證與補充的實際效果、連結檢查都沒有測到。
- 看圖路線（掃描檔、照片改用 Opus 5.5）只在模擬模式與單元測試中確認，沒有用真實的掃描檔跑過。
